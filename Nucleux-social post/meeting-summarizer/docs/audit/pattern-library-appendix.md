## A1. M3 deep spec per built pattern (S2 `material-patterns.js`, verbatim)

For the 29 patterns with an `available` M3 page. Fields: refined What/Why/When (S2), Anatomy, Content rules, Accessibility, Expressive (motion/shape), Metrics. (Intent, When-not, How, Variants, STATES, Flow and DON'Ts are in the main file §6/§7.)


### A1 · `disclosure` — Disclosure
- **What (M3):** A persistent indicator that a response, suggestion or action was generated by a model rather than authored by a person. It is not a legal footnote — it is a piece of the interface that is present at the moment the generated content is.
- **Why (M3):** It sets the boundary the rest of the relationship is built on. It is also the single most common regulatory and reputational requirement in enterprise AI, and the cheapest one to satisfy well.
- **When (M3):** At the surface of every AI-touched interaction, and unmissably on the first. If a user could plausibly mistake the output for a colleague's, disclosure is missing.
- **Expressive:** Every value in these previews resolves to a Material 3 token read out of the Design Kit — primary #6750A4, secondary-container #E8DEF8, tertiary-container #FFD8E4, outline-variant #CAC4D0, the 28dp extra-large corner and elevation 3, and Roboto at label-large 14/20/+0.1 and title-medium 16/24/+0.15. The marker is an assist chip rather than a bespoke pill because a reader already knows what a chip is. Motion is limited to two moments that carry meaning: the chip settles in with the content it marks, on M3’s emphasized easing with a small overshoot, and opening it grows the same element into a panel on a 0fr–1fr row rather than fading a popup in beside it. A marker that arrives late, or separately, is a marker a reader can miss.
- **S2 `pkg`:** `nucleux-m3-disclosure` — not an installed package (see main §1 item 4).

### A1 · `consent` — Consent
- **What (M3):** An explicit, scoped request to read data, connect a source, or act on the user's behalf. Scoped means the user can see exactly what is being asked for and can grant part of it.
- **Why (M3):** Consent that is bundled, pre-ticked or buried is not consent; it is a liability with a checkbox on it. A user who can decline one source and keep the rest will grant more overall, not less.
- **When (M3):** Before first access to any data source, before any action with an external effect, and again whenever the scope widens beyond what was granted.
- **Expressive:** This is the one place rose belongs on an onboarding surface: rose is where a human must act, and consent is the definition of that. The primary control is a capsule at full size because it is the largest decision on the screen; declining is a real button beside it, never a link in the corner.
- **S2 `pkg`:** `nucleux-m3-consent` — not an installed package (see main §1 item 4).

### A1 · `caveat` — Caveat
- **What (M3):** A short, muted line — "Aria can make mistakes. Check anything important." — rendered near the input and repeated beneath any output that is about to be acted on. It is a caption, not an alert.
- **Why (M3):** It manages expectations and reduces over-reliance at the moment of risk, which is the moment someone is about to send, publish or deploy something a model wrote. It also carries real liability weight for very little screen cost.
- **When (M3):** Persistently near the input, so it greets the user every session. Repeated beneath output that leaves the product — a message about to send, a document about to publish, a change about to deploy. Once per surface, not once per message.
- **Expressive:** Deliberately the quietest pattern in the set: body-small on on-surface-variant, no container of its own next to the input, and a surface-container strip only where it sits under output. It does not animate and it does not use the error role — this is a standing condition of the medium, not a fault, and colouring it as one would make people ignore the real errors.
- **S2 `pkg`:** `nucleux-m3-caveat` — not an installed package (see main §1 item 4).

### A1 · `avatar` — Avatar
- **What (M3):** One mark that stands for the agent wherever it appears — the thread, the toolbar, a notification, an activity log. It is the same shape at 24dp and 56dp, and it is never the same shape a person gets.
- **Why (M3):** A thread is read in glances, not in full. The mark is what the eye resolves before any label does, so it is doing the identification work whether it was designed for it or not. A generic circle, a stock headshot or a borrowed product logo all quietly claim something untrue.
- **When (M3):** Anywhere the agent authors, acts or waits: every generated turn, every activity entry, every surface where its work sits beside a person’s.
- **Expressive:** This is the neural expressive idea at its smallest: the mark is primary-container with the reserved glyph in primary, while a person is surface-container-highest with their initials — a different role, not a different shade, so the two separate before either is read. Working state is a ring animating on the mark itself rather than a spinner somewhere else on the screen, because state belongs to whatever it is a state of. Shape is corner-full throughout; only the glyph scales between 28, 40 and 56.
- **S2 `pkg`:** `nucleux-m3-avatar` — not an installed package (see main §1 item 4).

### A1 · `name` — Name
- **What (M3):** A single proper name the agent answers to, used identically in the interface, the documentation and the support conversation about it. It appears with a role beside it, so the name never has to carry the disclosure on its own.
- **Why (M3):** People need a handle to talk about a thing — "Aria got the number wrong" is a bug report, "the AI thing in the sidebar" is not. A name also sets expectations before a single word is generated: names that read as a human colleague quietly promise a colleague.
- **When (M3):** At first meeting, at the head of every generated turn, and in every place the agent is referred to in support, settings and release notes.
- **Expressive:** The name is title-medium on-surface with the role directly under it in body-medium on-surface-variant: a two-line list item, which is the M3 shape for exactly this — a thing and what it is. The assist chip beside it carries the disclosure so the name is never asked to imply it. Nothing about the treatment is decorative; the hierarchy is doing the work.
- **S2 `pkg`:** `nucleux-m3-name` — not an installed package (see main §1 item 4).

### A1 · `personality` — Personality
- **What (M3):** A written voice — a handful of rules about register, length, hedging and humour — applied to every generated string, with the things the agent will never do written down beside them.
- **Why (M3):** Voice is the part of an agent users actually experience, and it drifts without a spec: cheerful in onboarding, clinical in errors, apologetic under load. Inconsistency reads as instability, and an agent that performs feelings it does not have spends trust it will need later.
- **When (M3):** Everywhere text is generated, and especially in failure, refusal and uncertainty — the three moments where an undefined voice reaches for flattery or apology.
- **Expressive:** Voice is where the expressive system stops being visual: the same tokens hold, but what is being tuned is register. The rules card is surface-container-lowest with a primary tick for what the voice does and an outline tick for what it will not — one list, two weights, no red. The sample sits behind a primary rule because a voice defined only in adjectives is a voice nobody can implement.
- **S2 `pkg`:** `nucleux-m3-personality` — not an installed package (see main §1 item 4).

### A1 · `iconography` — Iconography
- **What (M3):** One glyph, reserved for generation, used at every entry point where a model does the work — and used nowhere else. Its containers change with the surface; the drawing never does.
- **Why (M3):** A reserved glyph is the cheapest way to make capability legible: a user learns it once in a menu and then recognises it in a toolbar, a field and a context menu without reading. Reserved is the operative word — a sparkle spent on "new" or "featured" teaches the opposite lesson and cannot be taken back.
- **When (M3):** On every control that triggers generation, and on nothing that does not.
- **Expressive:** The glyph is the same path used by the disclosure chip and the agent mark, which is what makes the vocabulary a vocabulary rather than three drawings. Three containers, all tokens: surface-container with the glyph in primary for quiet placements, secondary-container for tonal, primary with on-primary for a filled action. Nothing is animated — an icon that twinkles is decoration, and this glyph is a claim.
- **S2 `pkg`:** `nucleux-m3-iconography` — not an installed package (see main §1 item 4).

### A1 · `color` — Color
- **What (M3):** A small set of colour roles held back for the agent — its mark, its surfaces, its presence in a document someone else is editing — so that colour alone answers "is a model involved here".
- **Why (M3):** Colour is read before shape and long before text. If the agent has a reserved role, a user knows a surface is generated from across the room; if it borrows the product’s primary, the answer looks like the interface said it, which is precisely the confusion disclosure exists to prevent.
- **When (M3):** On the agent’s mark and surfaces, on presence in shared documents, and on the states of long-running work. Not as decoration on the surrounding product.
- **Expressive:** This is the load-bearing idea of the neural expressive language, stated in four roles: primary-container for the agent’s ground, on-primary-container for its text, primary for presence and working state, and the neutral surface tiers for anything a person authored. Shape reinforces it — the agent’s bubble takes the sharp corner on the left, the person’s on the right, so the pair still separates in greyscale. Colour is never the only signal, because roughly one reader in twelve cannot use it.
- **S2 `pkg`:** `nucleux-m3-color` — not an installed package (see main §1 item 4).

### A1 · `example-gallery` — Example Gallery
- **What (M3):** A browsable set of worked examples, each showing the ask AND what came back, with one control that puts the ask into the user’s own composer.
- **Why (M3):** A blank input is a terrible interface for a system whose range nobody can guess. Users do not fail to use an agent because it is weak; they fail because they cannot picture what a good request looks like. Examples answer that in seconds, and results answer it better than prompts do.
- **When (M3):** On empty states, at first run, and anywhere a user has to originate a request without a starting point. Also worth keeping reachable after onboarding — capability changes, and people re-learn range when it does.
- **Expressive:** Cards are surface-container-lowest on the large corner, lifting to elevation 2 on hover so the whole tile reads as pressable rather than only its link. The filters are M3 filter chips — selected state carries a leading tick as well as the tonal ground, because a filter that is only distinguishable by colour is a filter some readers cannot see.
- **S2 `pkg`:** `nucleux-m3-example-gallery` — not an installed package (see main §1 item 4).

### A1 · `templates` — Templates
- **What (M3):** A reusable request with named slots — audience, tone, source, length — that the user fills before it runs.
- **Why (M3):** Most poor results are poor requests. A template moves the difficulty from "what do I type" to "what do I want", which is a question users can answer. It also teaches: after a few passes people write the missing parts themselves and stop needing the scaffold.
- **When (M3):** For the requests people make repeatedly, and for the ones where a missing detail wastes a whole generation — anything with an audience, a format or a source.
- **Expressive:** An empty slot is dashed outline on transparent; a filled one is a solid secondary-container chip. The difference is shape and weight before it is colour, so a half-finished template reads as half-finished in greyscale. Slots settle rather than pop — filling one is a small change to a sentence, not an event.
- **S2 `pkg`:** `nucleux-m3-templates` — not an installed package (see main §1 item 4).

### A1 · `nudges` — Nudges
- **What (M3):** A small, anchored offer raised by the product rather than the user, pointing at a capability the current task would benefit from.
- **Why (M3):** Capability that is only in a menu is capability most people never find. A nudge earned by context — you have done this manually three times — is help; the same card on a timer is an advertisement, and users learn to close it without reading.
- **When (M3):** When the user’s behaviour is evidence the feature would help, and when the cost of ignoring it is zero. Never during an error, a payment, or anything the user is concentrating on.
- **Expressive:** Primary-container with a tail pointing at its anchor: the tail is what makes it a nudge rather than a notification, because it says which control is being talked about. It rises 6px with a small settle on entry — enough to be noticed once, not enough to interrupt — and leaves immediately on dismiss with no confirmation.
- **S2 `pkg`:** `nucleux-m3-nudges` — not an installed package (see main §1 item 4).

### A1 · `disclaimer` — Disclaimer
- **What (M3):** A standing statement of scope and limits, given in full once and reachable ever after from a compact line sitting beneath the composer.
- **Why (M3):** The other three patterns in this category sell capability. This one is the half that keeps the sale honest: a user who knows the edges trusts what is inside them, and a user who discovers a limit by being burned by it stops trusting all of it. It is also what makes over-reliance a choice rather than an accident.
- **When (M3):** At first run, before the first request. Then permanently reachable — next to the composer, in the agent’s own card, wherever someone would go to ask "can it do this?".
- **Expressive:** The full form is the M3 basic dialog — centred icon, headline-small, supporting text — on surface-container-high at elevation 3, because this is a moment the product is asking for a beat of attention. The compact form is a corner-full line at body-small, containing a real button rather than a link: reopening the statement is an action, and it must survive the reader forgetting where it was.
- **S2 `pkg`:** `nucleux-m3-disclaimer` — not an installed package (see main §1 item 4).

### A1 · `initial-cta` — Initial CTA
- **What (M3):** The main agent entry point for an empty workspace: the shared prompt composer drawn at its *initial* size, as the single focal point on the screen. It suggests the kind of request it expects, takes the keyboard the moment it is focused, grows with a multi-line request, and after the first send moves and shrinks into the ordinary working composer. It is a state of that one composer, not a component of its own.
- **Why (M3):** On a screen with nothing on it, the only useful thing to show is where to begin. Every mature assistant converged on the same answer — a centred, generous input, not a “Get started” button, a gallery or a hero — because a button only adds a step before the field, and a gallery answers a question the person has not asked. Making it the same composer as the working one matters as much: the person learns one control, the text they typed is never handed from one component to another, and the change of size is itself the signal that the workspace has gone from empty to working.
- **When (M3):** Whenever the main agent workspace has no conversation, task or history to show — a new conversation, a fresh project, a cleared thread. For people who already know agentic products as much as for anyone: this is not a tutorial, it is the empty state of the work surface.
- **Anatomy:**
  - **PromptComposer · initial** — The shared composer at its initial size — the same form every simulator docks, in one row — Add context, the field, voice, send — with the same padding, corner, type and height as Open Input’s composer. Container-aware: it fills a narrow surface and caps at a comfortable measure on a wide one.
  - **Field** — A textarea with a real accessible name (“Start a task with Aria”) and an active placeholder. It grows line by line to a ceiling the host chooses, then scrolls.
  - **SupportingLine** — Optional, one short line above the field: where this is and what the agent can reach. Second in the hierarchy; never a headline.
  - **SecondaryActions** — Add context, voice and the Model Selection chip, each at the working composer’s own emphasis. Add context on the left; model, voice and send on the right.
  - **Send** — The kit’s filled icon button. Disabled while empty, secondary emphasis while typing, primary once the request is ready. Named with its key shortcut.
  - **Hand-over** — On the first send: the request becomes the first turn, the agent starts, and the same composer moves and shrinks into the dock — measured before the repaint, animated from where it was.
- **Content rules:**
  - Write the placeholder as an action the person could take: “What would you like to work on?”, “Ask about this project…”, “Start with a task or question…”.
  - Never name the box: “Type here”, “Enter prompt”, “Message AI” and “Ask me anything” all hand the hard part — knowing what to ask — back to the reader.
  - One suggestion, not a tutorial. The placeholder disappears on the first keystroke, so anything that must stay readable belongs in the supporting line.
  - Keep the supporting line to one sentence of context — where this is, what the agent can reach — or leave it out.
  - Say which key sends, once, under the field. People move between assistants that disagree about Enter.
  - After the hand-over, the working placeholder is about continuing (“Reply, or add to the request”), not starting.
- **Accessibility:**
  - The field has an accessible name of its own; the placeholder is a suggestion and is never the only label (Material 3 text-field guidance).
  - The key hint is tied to the field with `aria-describedby`, and Send carries `aria-keyshortcuts` for whichever key the host uses.
  - Focus is visible as a colour and a shape change, not a colour alone.
  - Every control is a 48dp target — the kit’s Small icon buttons — including on the compact density.
  - Sending moves focus into the working field, so a keyboard user carries on where they were; the hand-over is announced through a polite live region.
  - The typed text is never lost in the transition: it becomes the first turn, and text typed into the working composer while the agent works stays in the field.
  - Under reduced motion the hand-over is instant; nothing about the state change depends on seeing it move.
- **Expressive:** Expression here is scale and one transition, and almost nothing else. The invitation looks exactly like Open Input’s composer — one row (Add context, the field, voice, send) with the same padding, corner, field type and height — so the invitation and the composer it becomes are visibly one object; what makes it the focal point is position, not size. Focus is a shape change rather than a halo: the outline takes the primary colour and the corner squares up a step, the same “this is now a working surface” move the working composer makes. The one expressive moment is the hand-over: the composer shrinks and moves to its docked place over 500 ms on the **emphasized** curve, without overshoot, because the system moved it rather than the person; the turns that caused it arrive a beat later on the **effects** role, from below. Under reduced motion the composer is simply in its new place.
- **Metrics:**
  - Time from the empty workspace to the first sent request, and how many sessions end without one.
  - How often the first request is abandoned after typing starts — a sign the placeholder promised something the field does not do.
  - The share of first requests that use a secondary action (context, voice, model). High means one of them may deserve more room; near zero means it may not deserve a place.
  - Share of first requests that are multi-line, which is the case for the ceiling you chose.
- **Precedent (names only):** ChatGPT · Claude · Gemini · Perplexity · Hugging Face Chat UI · Shape of AI — Initial CTA · Material 3 — Text fields
- **S2 `pkg`:** `nucleux-m3-initial-cta` — not an installed package (see main §1 item 4).

### A1 · `open-input` — Open Input
- **What (M3):** The shared prompt composer in its default working state: compact, docked under the conversation or task, and available after every response. It takes questions, instructions, follow-ups, edits and multi-step requests, short or long; grows with the request up to a ceiling and then scrolls; carries only the secondary controls the product supports; and keeps the person’s text through every other control, and through a failed send.
- **Why (M3):** It is the most-used control in any agentic product and the one most often shipped in a single state. The losses are small and constant: a half-written follow-up wiped by opening the model menu, a long request sent by an Enter meant as a new line, a failed send that clears the field and makes someone type it all again. Every mature assistant converged on the same working composer for the same reasons, and it is expensive to rediscover them one bug report at a time.
- **When (M3):** Wherever a person can make a request in words during ongoing work — conversational agents, task and coding agents, research tools, support agents, project workspaces, side panels — as the default entry point after the first request. Before any activity, the same composer is drawn at its larger Initial CTA size.
- **Anatomy:**
  - **PromptComposer · working** — The shared composer at its default size — the form every simulator docks and the Initial CTA hands over to. Compact (56px on one line), capped at the standard composer width, persistent.
  - **Field** — A textarea with a real label (“Message Aria”) and a placeholder in the product’s nouns. Grows to a ceiling, then scrolls inside itself.
  - **AddContext** — Left: the + menu for files and sources. Adds a chip to the request; never touches the text.
  - **SecondaryActions** — Right, before Send: the Model Selection chip (model and effort) and Voice, only where the product supports them.
  - **Send / Stop** — The kit’s filled icon button. Disabled until there is something to send; secondary while typing; primary when ready. While the agent answers it becomes Stop, in the same slot.
  - **ErrorRow** — A failed send, inside the composer above the untouched text: an icon, one sentence in human words, and Retry. Announced as an alert; the field is marked aria-invalid.
- **Content rules:**
  - Say what the field is for in the product’s nouns: “Ask about this project…”, “Reply to the customer…”, “Describe the change…”.
  - Don’t name the box: “Type here”, “Enter prompt” and “Message AI” tell nobody anything.
  - Write failures as what happened and what is kept: “Couldn’t send your request. It’s still here — edit it or try again.”
  - Word the three causes apart. A failed send can be retried now; offline waits for the connection; an unavailable agent waits for the agent — and never show a status code by default.
- **Accessibility:**
  - The field has its own accessible name; the placeholder is never the only label.
  - Send reports its state as disabled or enabled, and carries aria-keyshortcuts for the host’s key. No hint line is printed under the composer.
  - A failure is announced as an alert, linked to the field with aria-describedby, and the field is marked aria-invalid. The text is not cleared.
  - Focus is visible as colour and shape; every control is a 48dp target, at either density.
  - Opening a menu, changing the model or effort, and entering or leaving voice all return focus to the field with the caret at the end of the text.
  - Multi-line editing works with the keyboard alone: Shift + Enter (or Enter, in ⌘ / Ctrl + Enter mode) for a new line.
  - Under reduced motion the growth and the error row appear without animating.
- **Expressive:** Restrained on purpose: this is furniture somebody uses hundreds of times a day. Expression is spent only where it carries state. Focus is a shape change — the outline takes the primary colour and the corner squares up a step — not a glow. Growth eases the composer taller over 160 ms on the emphasized curve instead of jumping a line at a time. Ready gives Send the primary fill; while typing it is available at a secondary emphasis. A failure takes the error colour on the edge and one error-container row inside the composer, above the untouched text. Under reduced motion the growth and the error row simply appear.
- **Metrics:**
  - Sends followed within seconds by an edit of the same request — the sign of an accidental Enter.
  - Failed sends that are retried versus abandoned. Abandonment means the text or the way on was lost.
  - How often a secondary control is used mid-draft, and whether the draft survives it (it always should).
  - Share of requests that are multi-line, which is the case for the ceiling you chose.
- **Precedent (names only):** ChatGPT · Claude · Gemini · Perplexity · Microsoft Copilot · Cursor — send key · Material 3 — Text fields
- **S2 `pkg`:** `nucleux-m3-open-input` — not an installed package (see main §1 item 4).

### A1 · `suggested-prompts` — Suggested Prompts
- **What (M3):** A small, scannable set of contextual suggestions shown just below the shared composer before the conversation starts. Each is an action with a title (and, where there is room, one supporting line). Choosing one places its fuller prompt in the composer’s field as ordinary text: nothing is sent, nothing is locked, and every composer control still works. The rest of the set stays in view, the chosen one marked, so the person can choose another instead — it replaces the untouched text. The set steps aside as soon as the person writes or edits, and is gone once the conversation has begun.
- **Why (M3):** An empty field asks people to know what the agent is good for before they have seen it do anything. A few specific starting points answer that by example, on the person’s own material — but only if they are specific, few, and still the person’s to adjust. Generic examples (“Brainstorm ideas”) are ignored within a week; suggestions that send on press ask a request nobody read; and a wall of cards above the field becomes a menu competing with the thing it was meant to lead into.
- **When (M3):** On an empty or new conversation in a workspace with visible context worth asking about — a release plan, a research study, a design file, a ticket, a document — and in side panels opened next to that context. Wherever people hesitate over the first request.
- **Anatomy:**
  - **SuggestedPrompts** — The set: a section directly below the shared composer, no wider than it, named for assistive technology (no visible heading). Data-driven — it renders whatever suggestions the host derives from the workspace.
  - **Set name** — Says where the suggestions come from (“Suggested for the September release”). Not drawn: it is the set’s accessible name (aria-label), so the chips speak for themselves on screen.
  - **Suggestion** — One button: an 18dp icon (optional), a short action title, and — in the list or card layout — one supporting line saying what will happen. A Material suggestion chip, list row or compact outlined card.
  - **Prompt** — The fuller request a suggestion stands for (“Find the unresolved decisions blocking the September release.”). What lands in the composer; never shown as a locked preset.
  - **PromptComposer · working** — The shared Open Input composer, unchanged. The suggestion only ever puts words in its field; sending, context, model and voice are all the composer’s own.
  - **Provenance (optional)** — One quiet phrase under the composer — “Started from a suggestion”. Off by default. There is no key-hint line under this composer.
  - **Announcement** — A polite live-region message when a prompt is placed: what was placed, and that it can be edited or sent.
- **Content rules:**
  - Write each title as an action on something visible: “Find unresolved decisions”, “Compare customer themes”, “Suggest missing states”.
  - Keep titles to a few words; the prompt carries the detail. Keep a supporting line to one line — what will happen.
  - Make each one lead somewhere different. Three variations of “summarize” are one suggestion.
  - Avoid generic prompts — “Write something”, “Brainstorm ideas”, “Help me” — unless the product genuinely has nothing more specific to offer.
  - Name the set by its source for screen readers (“Suggested for the September release”), not “Try asking:”. No visible heading: the chips are self-explanatory under the composer.
  - Never base a suggestion on something the person cannot see or would not expect the product to know.
- **Accessibility:**
  - The set is a section named with aria-label (no visible heading); each suggestion is a native button, so Tab, Enter and Space all work. Arrow keys, Home and End also move between suggestions.
  - Each suggestion’s accessible name is its title; the supporting line and one shared sentence (“Places the request in the message field, to edit before you send”) are its description.
  - Choosing one moves focus to the composer’s field with the caret at the end, and a polite live region announces what was placed.
  - The selected emphasis is a change of fill as well as colour, and the result is text in the field, so nothing relies on colour alone.
  - When the set steps aside it leaves the tab order and the accessibility tree, not just the screen.
  - Every suggestion is a 48dp target at either density; focus is the kit’s visible ring.
  - Under reduced motion the hand-over and the collapse happen without animating.
- **Expressive:** Quiet on purpose: the composer is level one, the suggestions level two. Suggestion chips are the Nucleux `Md3Chip` (`@nucleux/md3-chip`, suggestion variant): outlined (or elevated), with an 18dp Material Symbol in primary; hover is a solid surface fill that keeps the stroke, and focus and press are the chip’s state layers. The one expressive moment is the hand-over: the chosen suggestion takes the secondary-container fill, and its title travels into the field over 420 ms on the emphasized-decelerate curve while the field’s own text fades in under it. When the person starts writing, the set collapses over 300 ms and leaves the tab order. Under reduced motion the text is simply there and the set simply goes.
- **Metrics:**
  - Share of first requests that start from a suggestion — and how many of those are edited before sending (edits mean the suggestion was a starting point, as intended).
  - Suggestions chosen and then cleared, which means the title promised something the prompt did not.
  - Which suggestions are never chosen: the candidates for replacing with something more specific.
  - Time from opening an empty workspace to the first request, with and without suggestions.
- **Precedent (names only):** ChatGPT · Claude · Gemini in Google Workspace · Microsoft 365 Copilot · Perplexity · Shape of AI — Suggestions · MUI X Chat & assistant-ui
- **S2 `pkg`:** `nucleux-m3-suggested-prompts` — not an installed package (see main §1 item 4).

### A1 · `ai-icons` — Icons
- **What (M3):** Four semantic roles, each drawn with one approved Material Symbol: **AI action** on the controls that run AI, **Generated with AI** on content AI wrote or changed, **Agent working** beside a status while the agent runs, and **Tool use** on the lines that say what the agent used. Every mark travels with words — a label, a tooltip or an accessible name.
- **Why (M3):** People scan a screen for two questions before they act: *which of these will run AI?* and *which of this did AI write?* One sparkle on everything answers neither. When the action, the provenance and the activity each have a shape of their own, the answer is visible at a glance, the habit transfers from one screen to the next, and the generated-content mark keeps its value as a signal of where to check.
- **When (M3):** Wherever a product mixes AI capability with ordinary controls and content: toolbars and menus with AI actions, fields the agent can fill, documents and records holding AI-written text, and any surface where the agent works in the background or reaches into other systems.
- **Anatomy:**
  - **AI action mark** — On controls that run AI on something specific. Shine star (`star_shine`) by default; Wand (`wand_shine`) approved. Carries the emphasis colour; never on content or decoration.
  - **Generated-content mark** — On content AI wrote or changed, in an outlined Md3Chip with its label (“Generated with AI”). Info bubble (`chat_info`) by default; Inserted (`import_spark`) approved. Pressing it explains what happened and offers Undo.
  - **Working mark** — Beside a status line while the agent is running (“Aria is rewriting…”), with Stop. `progress_activity`, turning. Gone the moment the work ends.
  - **Tool-use mark** — Leads the line naming a tool or system the agent used (“Looked up 2 tickets in Helpdesk”). Wrench (`build`) by default; Tools (`handyman`) approved.
  - **Words** — A verb label, a tooltip plus accessible name (“Summarize with AI”), a status, or a provenance label. The mark never carries meaning alone.
  - **Md3 components** — Md3Button (tonal) and Md3IconButton for actions, Md3Tooltip (plain, and rich for the explanation), Md3Chip for the generated mark, Md3TextField and Md3Card around them — all from the Nucleux MCP, with Material Symbols in place of the packages’ Lucide icons.
- **Content rules:**
  - Label AI actions with the verb for what happens — “Rewrite”, “Summarize account”, “Suggest a next step” — not “AI”, “Magic” or “Ask AI”.
  - Name icon-only AI actions “… with AI” (or with the agent’s name), so the mark and the name agree.
  - Label generated content plainly: “Generated with AI”, “Summarized by Aria”. Say what was used when it matters.
  - Write working status as what the agent is doing now: “Aria is reading the account…”, not “Thinking…”.
  - Name tools by the system and the act: “Looked up 2 tickets in Helpdesk”.
  - Mark new features with the word “New”, never with an AI mark.
- **Accessibility:**
  - Marks are decorative (aria-hidden) inside controls and labels; the meaning is in the label, the accessible name or the status text.
  - Every icon-only AI action has an accessible name and a tooltip referenced by aria-describedby; tooltips show on hover and on keyboard focus, and Escape hides them without moving focus.
  - Disabled AI actions use aria-disabled, so they stay focusable and can say why they are unavailable.
  - The working status is a polite live region; starting, finishing and stopping are announced.
  - The generated mark is a button with aria-expanded; its explanation is a rich tooltip that holds its own actions (Undo).
  - Each role has its own shape, so no meaning relies on colour; marks are 16–24px with 40–48px targets around them.
  - Under reduced motion the working mark does not turn and lines do not rise.
- **Expressive:** One mark moves, and only while it means “now”: the working mark turns steadily beside its status line — no pulse, no shimmer, no sparkle burst. The AI-action mark carries the emphasis colour (primary by default) in every control, so it differs from ordinary controls in colour *and* shape; the generated mark sits in an outlined Md3Chip with its label. Status and tool lines rise in over 300 ms on emphasized-decelerate; rewritten text fades in. Hover and focus are the components’ own 8% / 12% state layers; tooltips fade in 150 ms. Under reduced motion nothing turns or rises: the words carry the state.
- **Metrics:**
  - Audit: count AI marks on a screen that are not on an AI action, AI content, agent activity or a tool line. The target is zero.
  - First-use error rate on AI actions (pressed expecting something else), with and without the word.
  - Share of generated-content marks opened: low means it is ignored; very high may mean people do not trust what is unmarked.
  - In usability tests: can people say, for each control, whether it runs AI, and for each block, whether AI wrote it?
- **Precedent (names only):** Cloudscape (AWS) — Gen-AI iconography · IBM Carbon — AI label · Red Hat / PatternFly — AI iconography · Shape of AI — Iconography · Gemini, Claude & ChatGPT · Microsoft 365 Copilot
- **S2 `pkg`:** `nucleux-m3-ai-icons` — not an installed package (see main §1 item 4).

### A1 · `autocomplete` — Autocomplete
- **What (M3):** While someone types in the shared composer, the likely rest of a familiar request appears after the caret in a lighter colour, with the key that accepts it. Typing “/”, “@” or “#” opens a short menu of commands, people and files, or tools instead. Accepting inserts ordinary, editable text; nothing is sent until the person sends it.
- **Why (M3):** Many requests start the same way and end the same way. Finishing them saves time only if it costs no control: the suggestion has to be unmistakably not-yet-typed, easy to ignore, quick to dismiss, and, once taken, just text. Products that got this right (Smart Compose, Copilot) made accept a single key and kept Enter for sending what was written.
- **When (M3):** In a composer or field where people repeat requests, refer to commands, people, files or tools by name, and where a completion can be predicted from what they have typed so far.
- **Anatomy:**
  - **Shared composer** — The same Open Input composer. Autocomplete attaches to its field; it adds nothing else.
  - **Suggestion (inline)** — The rest of the request after the caret, in an aria-hidden overlay laid over the field — never in its value. Tappable to accept.
  - **Accept key** — A small outlined key at the end of the suggestion (Tab, or →). It appears only with a suggestion.
  - **Completion menu** — For /, @ and #: an Md3Menu listbox above the composer, with a heading (Commands, Mention, Tools); arrows move, Enter or Tab inserts, Escape closes. Focus stays in the field (aria-activedescendant).
  - **Announcement** — A polite message when a suggestion first appears and when one is accepted or dismissed, kept separate from the typed text.
  - **Provider** — Data the host supplies: phrases to complete, and the items for each trigger. The module has no product content.
- **Content rules:**
  - Completions finish requests in the person’s own phrasing; keep them short — a clause, not a paragraph.
  - Menu items: the command or name first, a short descriptor after (“summarize · Summarize a doc or thread”).
  - Announcements: “Suggestion: …. Tab to accept.”; “Accepted. Not sent.”; “Suggestion dismissed.”
- **Accessibility:**
  - The suggestion is not in the field’s value and the overlay is aria-hidden; the field has aria-autocomplete, and a polite live region announces the suggestion once, prefixed “Suggestion:”.
  - Menus are listboxes; the field keeps focus and points at the active option with aria-activedescendant and aria-expanded; arrows move, Enter or Tab inserts, Escape closes.
  - Accept is a single key that is not Enter, plus a tap target on the suggestion and its key; ⌘/Ctrl + → takes one word.
  - The suggestion differs from typed text in colour and is labelled by its key, and is announced in words.
  - Under reduced motion it appears without fading.
- **Expressive:** Quiet by design: the suggestion fades in over 150 ms in on-surface-variant at reduced opacity (Subtle) or full (Standard) — a different colour from what was typed either way — with a small outlined key at its end. Menus are Md3Menu listboxes that open above a docked composer. No shimmer, no typing animation: the text is simply there, or simply gone. Under reduced motion it does not fade.
- **Metrics:**
  - Acceptance rate, and how often accepted text is then edited before sending.
  - Dismissals per suggestion shown (high means it guesses too early or too often).
  - Characters saved per request.
  - Sends that include text accepted and not read back (look for quick accept-then-send on long completions).
- **Precedent (names only):** Gmail — Smart Compose · GitHub Copilot in VS Code · Claude, ChatGPT, Cursor, Slack · GitHub Copilot Chat · WAI-ARIA — combobox with autocomplete
- **S2 `pkg`:** `nucleux-m3-autocomplete` — not an installed package (see main §1 item 4).

### A1 · `proactive` — Proactive Suggestions
- **What (M3):** A compact card, placed where the work is, that says who is suggesting, why it appeared (“Two release blockers have no owner since Sam Ortiz moved to Payments”), what it recommends (“Assign owners before the release?”) and three ways out: Review, Remind me tomorrow, Dismiss. Review opens the relevant workflow with a proposal the person confirms.
- **Why (M3):** Agents see more of the workspace than a person scanning it, so they can catch what is about to go wrong. That only helps if the suggestion explains itself, never acts on its own, and goes away when told to: products that nag train people to ignore them, and products that act unasked lose trust the first time they are wrong.
- **When (M3):** During ongoing work, when a specific, checkable condition becomes true and there is a clear next step: unowned blockers before a release, an unanswered email, a duplicate issue, a missed deadline, a step left out of a checklist.
- **Anatomy:**
  - **Provenance** — Who is suggesting (“Suggested by Aria”), with the generated-content mark.
  - **Reason** — Why it appeared, from what was noticed — specific and checkable.
  - **Suggested action** — The recommendation, phrased as one (“Assign owners before the release?”), never in the past tense.
  - **Primary action** — Md3Button: Review. Opens the workflow with a proposal; changes nothing by itself.
  - **Snooze / Dismiss** — Md3Buttons (text). Snooze hides it until a time and returns only if still true; Dismiss removes it and is remembered for that evidence, with Undo.
  - **Review** — The host’s own workflow (here, an Md3Card listing proposed owners, each changeable) and one confirming action, with Undo afterwards.
  - **Status line** — A polite note for what just happened — dismissed, snoozed, resolved, done — with Undo where it applies.
- **Content rules:**
  - Reason: the evidence, specifically — counts, names, dates. “Two release blockers have no owner since Sam Ortiz moved to Payments.”
  - Action: a recommendation — a question or “Suggest…”. Never past tense; never “Fixed”.
  - Primary: Review (or Open, See options). The verb that changes things belongs in the review: “Assign 2 owners”.
  - After: say what happened and who decided — “you confirmed Aria’s proposal” — with Undo.
- **Accessibility:**
  - The card is a region named “Suggestion from Aria”; the primary action is described by the reason and the recommendation.
  - Appearing, preparing, dismissing, snoozing, resolving and finishing are announced in a polite live region; nothing steals focus when it appears.
  - Every action is a native button with a 40dp+ target; Undo is reachable from the keyboard right after.
  - The review is a labelled region; each “Change” is named for its issue.
  - Under reduced motion it neither rises nor fades.
- **Expressive:** It arrives, it does not interrupt: the card rises in over 400 ms on emphasized-decelerate, in secondary-container (tonal) or outlined, at comfortable or compact density. The provenance line uses the generated-content mark from the Icons vocabulary — this text came from the agent — and “Preparing a review” uses the working mark. When the reason goes away it says “Resolved” and fades over two seconds; dismissing is instant. Under reduced motion nothing rises or fades.
- **Metrics:**
  - Acceptance rate per kind of suggestion, and how often the proposal is changed before confirming.
  - Dismissals per suggestion shown (high means it is not useful, or arrives at the wrong time).
  - Snoozes that end in acceptance.
  - Undo after confirming (a proposal that looked right but was not).
- **Precedent (names only):** Linear — Triage Intelligence · Gmail — Nudges · Microsoft HAX Toolkit · GitHub Copilot — next edit suggestions
- **S2 `pkg`:** `nucleux-m3-proactive` — not an installed package (see main §1 item 4).

### A1 · `randomize` — Randomize
- **What (M3):** One optional control (“Try a direction”) beside the shared composer. Pressing it shows one generated direction: a title and a line, with Use this and Generate another, and a way back to the previous one. Use this puts an editable prompt in the composer — asking first if the composer already holds the person’s words.
- **Why (M3):** A blank page is hardest exactly where there is no right answer: brainstorming, creative briefs, styles. A random starting point breaks the blank page cheaply. It only helps if it stays a starting point — editable, optional, and never allowed to overwrite what someone has already written.
- **When (M3):** Creative and exploratory work where variety is the point and nothing is at stake: campaign directions, naming, ideas, visual styles, presets, prompt inspiration, starting configurations for generative tools.
- **Intent (M3):** Help people explore alternatives — campaign angles, ideas, styles, presets — without inventing every one themselves, while the composer stays theirs.
- **When not (M3):** Not in finance, legal, medical, safety, destructive or otherwise deterministic workflows, where a random “direction” has no value and may mislead. Not as a replacement for open input, and not as a disguised way to run something.
- **How (M3):** Offer it as one labelled, optional control that says what you get. Show one direction at a time, marked as generated; let people generate another (never a repeat this round) and step back. Place it on Use this as ordinary, editable composer text, focus there, and send nothing. If the composer has the person’s own words, ask: replace, add below, or cancel. Constrain the generator so every direction is usable.
- **Variants (M3):**
  - **“Use this” / Place automatically** — Automatic placement fills an empty composer as each direction arrives; with a draft it still asks.
  - **Icon: AI action / Shuffle / Dice** — The AI action mark by default, because a model runs; shuffle or dice where “another one” is the clearer promise.
  - **Tonal / Text** — Tonal to be found in an empty workspace; text where it sits beside other tools.
- **STATES (M3):**
  - **Ready** — *Trigger:* an exploratory workspace. *Behaviour:* one optional control; the composer works alone. *Next:* Generating.
  - **Generating** — *Trigger:* the control or Generate another. *Behaviour:* the working mark, briefly. *Next:* New suggestion.
  - **New suggestion** — *Trigger:* a direction came back. *Behaviour:* one direction, marked generated; Use this, Generate another. *Next:* Applied, Generate another.
  - **Generate another** — *Trigger:* asked for another. *Behaviour:* a different direction (never a repeat this round), with a count and Previous. *Next:* Applied.
  - **Replace confirmation** — *Trigger:* Use this while the composer holds the person’s words. *Behaviour:* replace, add below, or cancel. *Next:* Applied, or back.
  - **Applied to composer** — *Trigger:* placed. *Behaviour:* editable prompt, focus and caret there; nothing sent. *Next:* the conversation.
- **Anatomy:**
  - **Control** — Md3Button (tonal or text) with its icon and a label that says what you get (“Try a direction”), plus one supporting line.
  - **Direction** — A compact card: “Generated direction · 2 of 3” with the generated mark and a Previous button; the title; one line.
  - **Use this / Generate another** — Md3Buttons. Use this places the prompt; Generate another replaces the card with a new direction.
  - **Replace confirmation** — Inline, in the card: “Replace your draft with this direction?” — Replace draft, Add below my draft, Cancel.
  - **Shared composer** — The Open Input composer, unchanged. The direction lands there as editable text; the person sends it.
- **Content rules:**
  - Label what you get: “Try a direction”, “Another idea”, “Random style” — not “Random” or “Surprise me” alone.
  - A direction is a short title and one line. The placed prompt wraps it in the request it stands for.
  - Confirmation: “Replace your draft with this direction?” — never replace silently.
- **Accessibility:**
  - The control is a native button described by its supporting line; the direction is a labelled group; the confirmation is an inline alertdialog with its own question.
  - Each new direction is announced in a polite live region (title and line); placing it moves focus to the composer with the caret at the end.
  - Previous is a named icon button; every action is reachable by keyboard.
  - Under reduced motion directions appear without rising.
- **Expressive:** Ready → generating → new result, and nothing more: the working mark with “Finding a different direction…”, then the direction card rises in over 400 ms on emphasized-decelerate. The control carries the AI-action mark by default (it runs a model, per the Icons vocabulary), or shuffle or dice; the result carries the generated-content mark. No dice animation, no confetti. Under reduced motion it simply appears.
- **Metrics:**
  - Directions generated per use, and how many end in Use this.
  - Placed prompts that are edited before sending (a good sign: it was a starting point).
  - Replace confirmations answered with Add below or Cancel (people protecting their own work).
- **Precedent (names only):** Shape of AI — Randomize · Krea · Scenario · Coolors
- **S2 `pkg`:** `nucleux-m3-randomize` — not an installed package (see main §1 item 4).

### A1 · `voice-input` — Voice Input
- **What (M3):** The ordinary composer, with a microphone in it. Pressing it (after a plain-words permission request the first time) turns the same bar into a voice session: a lit microphone with a dot and a running clock, the words as they are heard after anything already typed, and Pause, Stop and Cancel. Stop ends capture and puts the transcript in the field, marked **From voice** with Undo — it never sends. The person edits it and sends it like anything typed. A soft gradient behind the bar answers the voice and is gone when voice ends.
- **Why (M3):** Voice is the input people reach for when typing is slow, awkward or impractical — which is exactly when a silent mistake is most expensive. Nearly everything that goes wrong here is either a state that was never designed or a decision to build too much: the microphone that is open and does not look it, the animation that runs whether or not anything is heard, the failure that takes the keyboard away with it, and the voice mode that becomes a screen of its own and throws away the work the question was about.
- **When (M3):** Wherever a request is quicker said than typed, and the product already has a composer to say it into. Not as a novelty alternative to a keyboard that is there and working, and not at all where the request commits something that a misheard word would commit wrongly — there, hold the text for correction first.
- **Anatomy:**
  - **Shared composer** — The same AgentComposer in every state. Voice changes what the bar contains, not which bar it is.
  - **Microphone control** — In the bar at rest (“Speak instead of typing”); unavailable with its reason when there is no microphone.
  - **Permission panel** — Above the bar, not a modal: what, why, when it is on, how to stop. Allow microphone / Not now.
  - **Active-capture indicator** — Lit microphone with a dot, the voice activity strokes, and “Listening · 0:04”. Persistent for the whole capture.
  - **Heard line** — What was typed, then the words as they are heard (two lines, clipped).
  - **Pause / Resume · Stop · Cancel** — Pause keeps progress; Stop keeps the words and never sends; Cancel discards this recording and keeps typed text.
  - **From-voice marker** — “From voice — check it before you send”, with Undo, above the field once the words land.
  - **Recovery panel** — Couldn’t understand: what was heard, Retry, Edit captured text, Type instead.
  - **Voice gradient** — Behind the bar only while voice is on; answers each word, settles in silence, drifts while transcribing, gone after.
- **Content rules:**
  - Name the state in words beside the clock: “Listening · 0:04”, “Paused · microphone off”, “Transcribing…”.
  - Ask for the microphone in plain words: what it is for, when it is on, how to stop it.
  - Label controls by what they do to the words: “Stop — keeps what you said”, “Cancel — discard this recording, your typed text stays”.
  - Mark the result: “From voice — check it before you send”, with Undo.
  - When it fails, say what happened (“Couldn’t make out all of that”) — never only “Something went wrong” — and offer Retry, Edit captured text and Type instead.
- **Accessibility:**
  - Every state change is announced in a polite live region in words (“Microphone on. Listening.”, “Paused…”, “Transcribed into the message… Nothing was sent.”) — never the animation.
  - Pause, Resume, Stop and Cancel are buttons with accessible names that say what happens to the words.
  - The microphone is never the only route: the field stays in the same bar, and Unavailable / Not now return focus to it.
  - Capture is shown by shape and words (lit microphone, dot, clock, label), not by colour alone.
  - Targets are 40px (48px on phones); the voice session does not wrap into two rows.
  - Under reduced motion the gradient and the dot are still; the indicator is pinned; the words carry each state.
- **Expressive:** The bar is the expression. While the microphone is on, a soft, low-contrast gradient sits behind the composer and answers the voice: each word swells it a little (≈4% scale, a short opacity rise), silence lets it settle, Pause dims it, transcribing turns its 18-second drift into a slow 14-second directional flow, and it fades away the moment the words land in the field. No orb, no full-screen glow, no colour change on error — errors use the semantic error accent in the panel and motion stops. Under reduced motion the gradient is still and the words carry every state.
- **Metrics:**
  - How often the microphone is pressed and then cancelled without anything being said, which measures whether people can tell the bar is listening.
  - How often a voice request is followed immediately by the same request typed — the signal that recognition is failing quietly.
  - Requests sent with an empty or near-empty result, which measures whether silence is being answered or forwarded.
  - Whether voice is used at all on the scenarios that offer it. A microphone nobody presses is a control to remove, not a control to make louder.
- **Precedent (names only):** ChatGPT — dictation and Voice · Microsoft 365 Copilot Chat — dictate messages · Gemini Live · Platform microphone indicators (iOS, Android, browsers)
- **S2 `pkg`:** `nucleux-m3-voice-input` — not an installed package (see main §1 item 4).

### A1 · `visual-input` — Visual Input
- **What (M3):** Under + in the shared composer: Upload image, Take photo, Choose a recent screenshot, Share screen — only the sources the product allows. What was chosen lands as a card with a real preview above the words (never replacing them), saying what the agent will see and when, with Replace and Remove. Nothing is read until Send. Sharing a window starts with a choice of the one window, and while it is on a persistent bar with a red dot says so and offers Stop sharing; stopping never ends the conversation. When the agent answers it names the visual it used.
- **Why (M3):** Two things go wrong here and they are opposites. The first is answering too early: an image on its own is not a question, and a product that responds the moment one lands is guessing at intent — the same screenshot could mean “what is this error?”, “is this the same bug as last week?” or “write me the fix”. The second is answering too vaguely: a photograph carries far more than the model reliably reads, and an answer that does not say which part it used, or what was too dark or out of frame to judge, cannot be checked at all.
- **When (M3):** Where the evidence is visual and describing it in words is slower or less accurate: error screens and stack traces, damage and defects, whiteboards, receipts, labels, charts in somebody else’s document, field and medical photographs.
- **Intent (M3):** Visual context joins the request in the shared composer: recognisable, removable, combined with words — and screen sharing is a visible, stoppable state.
- **How (M3):** Make the visual part of THIS request: a card in the composer with a preview big enough to recognise, the name, the line “Aria will see this when you send”, Replace and Remove. Explain camera and screen access in words before anything is captured — what, why, when it is on, how to stop — and let people choose the one window. Keep sharing visible for as long as it is on, and put Stop sharing next to the indicator. If a file cannot be used, say what can; if an image cannot be read, keep the message and offer Retry, Replace and Continue without it. Never let a visual trigger an action on its own.
- **Variants (M3):**
  - **Upload or recent screenshot** — A file joins the request as a card; nothing is read until Send.
  - **Take photo** — Camera permission first, in words; the camera is on only while the photo is taken.
  - **Share screen** — One chosen window, a persistent sharing bar and Stop sharing; stopping never ends the conversation.
- **STATES (M3):**
  - **No visual** — *Trigger:* nothing shown yet. *Behaviour:* the composer; + offers sources. *Meaning:* the agent only has your words. *Action:* +. *Next:* Selecting.
  - **Selecting** — *Trigger:* + pressed. *Behaviour:* only the allowed sources are listed. *Meaning:* nothing shared yet. *Action:* choose, or close. *Next:* Attached, Permission, Unsupported.
  - **Visual attached** — *Trigger:* an image chosen. *Behaviour:* a preview card in the composer with Replace and Remove; words unchanged. *Meaning:* this is what the agent will see, when you send. *Action:* add words, Replace, Remove, Send. *Next:* Processing.
  - **Sharing** — *Trigger:* a window chosen. *Behaviour:* persistent bar with a red dot and Stop sharing; the card is live; the window has a soft boundary. *Meaning:* the agent can see this window until you stop. *Action:* ask, or Stop sharing. *Next:* Processing, or No visual — the conversation continues.
  - **Processing** — *Trigger:* sent with a visual. *Behaviour:* “Aria is reading this image…” and a slow sheen. *Meaning:* the visual is being used now. *Action:* wait. *Next:* Ready or Failed.
  - **Ready** — *Trigger:* the agent finished. *Behaviour:* the message carries the visual; the answer says which visual it used. *Meaning:* you can see what the answer is based on. *Action:* follow up. *Next:* No visual.
  - **Permission required** — *Trigger:* camera or screen chosen. *Behaviour:* what, why, when, how to stop — and the one window to pick. *Meaning:* nothing captured yet. *Action:* choose / Allow, or Cancel. *Next:* Sharing / Attached, or No visual.
  - **Unsupported** — *Trigger:* a file that cannot be used. *Behaviour:* says what can be used; words kept. *Meaning:* nothing added. *Action:* choose an image, or continue without it. *Next:* Selecting or No visual.
  - **Failed** — *Trigger:* the image could not be read. *Behaviour:* the card is marked; the message is kept; nothing was sent without it. *Meaning:* nothing lost. *Action:* Retry, Replace, Continue without it. *Next:* Processing, Selecting or No visual.
- **Anatomy:**
  - **+ menu** — In the shared composer: only the sources the product allows — Upload image, Take photo, Choose a recent screenshot, Share screen.
  - **Visual card** — Above the words in the composer: a real preview, the name, “Aria will see this when you send”, Replace and Remove.
  - **Permission panel** — Before camera or screen: what is needed, why, when it is on, how to stop — and the one window to choose.
  - **Sharing bar** — Persistent while a window is shared: a red dot, “Sharing ‘Q3 metrics dashboard’”, Stop sharing.
  - **Shared boundary** — A soft outline and a “Shared with Aria” tag on the shared window only.
  - **Used line** — On the answer: “Used: dashboard-sep.png”.
  - **Failure panel** — Why it could not be read, with Retry, Replace and Continue without it; the message is kept.
- **Content rules:**
  - Say what the agent will see, and when: “Aria will see this when you send”.
  - Explain access before asking for it: “Only the window you choose will be shared. You’ll see “Sharing” while it’s on, and you can stop at any time.”
  - Name the visual in the answer: “Used: dashboard-sep.png”.
  - Unsupported says what can be used: “Aria can read images (PNG, JPG, HEIC). For a video, share your screen while it plays.”
  - Failure keeps the message: “Couldn’t read the image — it’s too blurry. Your message is kept.”
- **Accessibility:**
  - The card is a labelled group (“Visual context: dashboard-sep.png. Aria will see this when you send”); Replace and Remove name the image.
  - Sharing is announced when it starts and stops; the bar is a status region with a real Stop sharing button next to it.
  - Visual input is never the only route: everything can also be described in words in the same composer.
  - Failures and unsupported files are alerts with the next step as buttons; the message is kept.
  - Active sharing is shown by words, an icon and a dot, not colour alone; the dot and sheen stop under reduced motion.
- **Expressive:** Expression sits on the visual itself: the card rises into the composer from below, a slow, low-contrast sheen crosses the preview while the agent reads it, and the shared window gets a soft boundary and a “Shared with Aria” tag — the window, never the whole screen. The active-sharing dot breathes slowly. Under reduced motion all of it is still and the words carry the state.
- **Metrics:**
  - Visuals removed or replaced before sending — the preview doing its job.
  - Sharing sessions stopped by the person vs left running; time to Stop sharing.
  - Failed reads, and which way on (Retry, Replace, Continue without it).
  - Answers that name the visual they used.
- **Precedent (names only):** Gemini Live — camera and screen sharing · Microsoft Copilot Vision · ChatGPT image input

### A1 · `handwriting` — Handwriting Input
- **What (M3):** A pen button in the shared composer opens a writing pad above it; the composer stays where it was and keeps whatever was typed. Strokes appear as they are drawn, with Undo for the last stroke and Clear for all of it. Recognize reads the ink and shows the result under it — the ink stays in view. A word the recognizer was unsure of is a button marked “?” with alternatives, and Add to message waits until it is settled. Added text joins the typed words (never replacing them), marked “From handwriting” with Undo, and the ink can travel with the message as the original. If the writing cannot be read, nothing is guessed: Rewrite, Retry, Keep original or Switch to typing.
- **Why (M3):** Recognition is a reading, not a fact. If it is silently accepted, a wrong word (“flaw” for “flow”) becomes the instruction, and nobody can see where it came from. Keeping the three layers apart — what was written, what was read, what you accepted — is what lets a person trust handwriting as a way to write a request, and lets the agent work from words the person actually chose.
- **When (M3):** On pen- and touch-capable surfaces, for short requests, notes and annotations where writing is quicker or more natural than typing. Not as the only way in: the field always works, and on a device without pen or touch the pen is shown unavailable and typing carries on.
- **Intent (M3):** A pen in the shared composer. Handwriting, recognized text and accepted text stay distinct, and nothing uncertain is ever accepted silently.
- **How (M3):** Put handwriting in the composer people already use — a pen button, not a separate composer. Open the pad above the field and keep what was typed. Show the ink as drawn; offer Undo stroke and Clear. Recognize on request (or after a pause, if the product converts automatically) and show the reading under the ink. Mark uncertain words, offer the likely alternatives, and block Add to message until they are settled. Append — never overwrite — and mark the result “From handwriting” with Undo. Keep the original ink as context unless the person removes it. On failure, keep the ink and offer Rewrite, Retry, Keep original and Switch to typing. Never send anything because writing finished.
- **Variants (M3):**
  - **Review first (default)** — Recognize on request and show the reading before anything joins the message. Right for requests, where a misread word changes the instruction.
  - **Convert automatically** — Recognize after a pause and add the text when every word is certain. Uncertain words still stop for a look, and the From-handwriting marker and Undo are always there.
  - **Original only** — Keep original after a failure: the ink is attached as an image and no text is guessed — for sketches, signatures or writing that is the point in itself.
- **STATES (M3):**
  - **Ready** — *Trigger:* the pen was pressed. *Behaviour:* the pad opens above the composer, which keeps what was typed. *Meaning:* nothing written yet. *Action:* write, or Close. *Next:* Writing.
  - **Writing** — *Trigger:* ink on the pad. *Behaviour:* strokes as drawn; Undo stroke, Clear, Recognize. *Meaning:* the ink is the original, not text yet. *Action:* keep writing, Undo, Clear, Recognize. *Next:* Recognizing.
  - **Recognizing** — *Trigger:* Recognize (or a pause, in automatic mode). *Behaviour:* status text; a slow sheen over the ink, which stays in view. *Meaning:* being read; nothing added. *Action:* wait. *Next:* Recognized or Couldn’t recognize.
  - **Recognized** — *Trigger:* recognition finished. *Behaviour:* the reading under the ink; uncertain words are buttons marked “?”; Add to message disabled while any remain. *Meaning:* what was read, not yet what you said. *Action:* settle the word, or Edit text. *Next:* Editing recognition or Added.
  - **Editing recognition** — *Trigger:* a word corrected. *Behaviour:* the corrected word is marked as yours; Add enabled. *Meaning:* it reads right; still not in the message. *Action:* Add to message. *Next:* Added to message.
  - **Added to message** — *Trigger:* Add to message. *Behaviour:* appended to the typed words, marked From handwriting with Undo; the ink attached as Handwritten note. *Meaning:* accepted text; nothing sent. *Action:* edit, Undo, remove the original, Send. *Next:* Ready.
  - **Couldn’t recognize** — *Trigger:* too little could be read. *Behaviour:* says so; the ink is kept; nothing guessed. *Meaning:* nothing lost, nothing added. *Action:* Rewrite, Retry, Keep original, Switch to typing. *Next:* Ready, Recognizing, or Added (original only).
  - **Unavailable** — *Trigger:* no pen or touch input. *Behaviour:* the pen explains why; the field works as always. *Meaning:* typing never depends on handwriting. *Action:* type instead. *Next:* —
- **Anatomy:**
  - **Pen button** — In the shared composer, beside the microphone. Pressed while the pad is open; disabled-looking (but explainable) when handwriting is unavailable.
  - **Writing pad** — Above the composer, never instead of it. A ruled surface with the status line, Undo stroke, Clear and Close.
  - **Ink** — Exactly what was drawn. Kept on the pad through recognizing and failure, and optionally attached to the message as the original.
  - **Recognized strip** — Under the ink: “Recognized”, the words, and any uncertain word as a button marked “?” with alternatives.
  - **Add to message** — The one step that turns recognized text into accepted text. Disabled while anything is uncertain.
  - **From-handwriting marker** — On the composer after adding: says where the words came from, with Undo that restores exactly what was typed.
  - **Handwritten note chip** — The original ink travelling with the message, removable without removing the words.
- **Content rules:**
  - Say what is happening while the ink is read: “Recognizing your writing…”.
  - Name the uncertainty, and how to settle it: “1 word needs a look — tap it to choose.”
  - Say where accepted text came from: “From handwriting — check it before you send”.
  - Failure says what happened and what is kept: “Couldn’t recognize this writing. Your ink is kept.” — never “Error”.
  - Unavailable says why and what to do: “This device has no pen or touch input. Type your request instead.”
- **Accessibility:**
  - The pen button is labelled “Write by hand” and reports pressed while the pad is open; when unavailable it stays focusable and explains why.
  - The pad is a labelled region; Undo stroke, Clear and Close are real buttons with names.
  - Recognizing, recognized, corrections and additions are announced in a polite live region.
  - The uncertain word is a button (“flaw — not sure about this word. Choose the right one”) and its alternatives are buttons — not colour alone: a “?” and a dotted underline mark it too.
  - Handwriting is never the only route: the same composer takes typed text, and Switch to typing is offered on failure.
  - After Add, Undo or Type instead, focus returns to the field; the sheen and writing animation stop under reduced motion.
- **Expressive:** The ink is never smoothed or beautified — it is the original. While it is being read, a slow, low-contrast sheen crosses the pad and the ink stays visible beneath it. The uncertain word carries a dotted underline and a “?” in the error tone (stronger or subtler by setting), and a corrected word settles into the agent’s primary. Text added to the composer arrives with the “From handwriting” marker. Under reduced motion the sheen and the writing animation stop; the words carry every state.
- **Metrics:**
  - How often an uncertain word is corrected versus left as first read — a high correction rate on one word is a recognizer problem worth fixing.
  - Undo after Add to message: how often added handwriting is taken back out.
  - Couldn’t recognize → which way on (Rewrite, Retry, Keep original, Switch to typing).
  - Messages sent with the original ink attached, and how often the original is removed before sending.
- **Precedent (names only):** Stylus input in text fields — Android · Scribble — iPadOS · Ink kept as ink — note-taking apps
- **S2 `pkg`:** `nucleux-m3-handwriting` — not an installed package (see main §1 item 4).

### A1 · `gesture` — Gesture Input
- **What (M3):** Select on screen in the shared composer turns on a visible selecting mode: a toolbar on the content (Circle, Highlight, Tap, Region, Cancel) and every selectable item becomes a button, so Tab and Enter select the same things. A gesture that lands on one thing puts a boundary around it and names it, with Add to message, Adjust and Clear. Added context is a chip in the composer — “Selected: Conversion chart” — with ✕. When the agent uses it, the thing says so; the answer names what it used. A gesture that covers two things asks which; one that covers nothing says so; Describe it instead is always offered.
- **Why (M3):** “Why did this drop?” only means something if the agent knows what “this” is. Pointing is the fastest way to say it, but a selection that is guessed, invisible or silently added sends the agent to the wrong thing — and a gesture that triggers an action is a gesture nobody can use safely. Naming the selection, keeping it removable, and asking when it is ambiguous make pointing trustworthy.
- **When (M3):** Wherever a request is about something already on screen: a chart, a row, a region of a design, a paragraph. Not as the only way to refer to things — words always work — and never as a way to trigger actions.
- **Anatomy:**
  - **Select on screen** — A button in the shared composer, pressed while selecting.
  - **Selecting toolbar** — On the content: what to do (“Circle what you mean — or Tab to it”), the allowed gestures, and Cancel.
  - **Targets** — The things that can be selected. Each is a real button while selecting, so the keyboard reaches all of them.
  - **Boundary** — Around the selected thing only. Dashed, solid or glow by setting.
  - **Selection bar** — Names what was selected, with Adjust, Clear and Add to message.
  - **Context chip** — In the composer: “Selected: Conversion chart”, with ✕.
  - **Using tag** — “Aria is looking at this” on the selection while the agent uses it.
  - **Ambiguity panel** — Above the composer: “Which did you mean?”, a button per candidate, Try again, Describe it instead, Clear.
- **Content rules:**
  - Name the selection by what it is: “Selected: Conversion chart” — not “Selection added”.
  - Say what the agent is using while it uses it: “Aria is looking at this”.
  - Ambiguity is a question: “Your selection covers more than one thing. Which did you mean?”
  - Say what clearing means: “Selection cleared — Aria won’t use the Conversion chart.”
  - In the answer, name the selection first: “In the Conversion chart: …”.
- **Accessibility:**
  - Select on screen is a toggle button (aria-pressed); focus moves to the gesture toolbar when selecting starts.
  - Every target is a real button while selecting (“Select Conversion chart”), so Tab and Enter select without drawing.
  - Escape cancels selecting from anywhere in the pattern.
  - Selection, adding, removing, using and clearing are announced in a polite live region; ambiguity is an alert with buttons.
  - Selection is shown by a boundary, a tag and words, not colour alone; Describe it instead is always available.
  - Sheen and draw-in animations stop under reduced motion; targets are at least 48px on touch.
- **Expressive:** The boundary sits on the selected thing only — dashed, solid or a soft glow — never around the whole screen. The circle draws as you draw it, in the primary colour, and the selection settles onto the element it snaps to. While the agent uses it, a slow, low-contrast sheen crosses that element under “Aria is looking at this”. Candidates in an ambiguous selection are marked in the tertiary tone. Under reduced motion nothing moves; words and boundaries carry the state.
- **Metrics:**
  - How often a selection is adjusted or cleared before sending — high numbers mean snapping is landing on the wrong thing.
  - Ambiguous selections, and which way on (choose, retry, describe, clear).
  - Answers that name the selection they used, and follow-ups that reuse it.
  - Keyboard selections vs gesture selections.
- **Precedent (names only):** Circle to Search — Android · Screenshot, then ask — chat assistants · Select, then act — every desktop OS
- **S2 `pkg`:** `nucleux-m3-selection` — not an installed package (see main §1 item 4).

### A1 · `structured-input` — Structured Input
- **What (M3):** The person asks in the ordinary composer (“Create a follow-up task for this blocker”). Aria answers with a compact form — Task, Owner, Due date, Priority — with visible labels, helper text and required marks. Values Aria suggested are marked “Suggested”, with why, and stay editable; a changed value is marked “Edited by you” and never changed back. Review checks every field and puts each problem next to its field. A review step shows the values and exactly what Aria will receive, and waits for Create task. Success shows the outcome, what Aria received and Undo; failure keeps every value and offers Retry. The composer stays available the whole time.
- **Why (M3):** Free text is the right way to ask, and the wrong way to set a date or pick an owner. A form makes the values exact and checkable — but only if suggestions are visible as suggestions, nothing the person set is overwritten, errors say how to fix them, and anything that changes another system is reviewed first. Showing what the agent receives closes the loop: the person can see the request the agent will act on, not just the one they typed.
- **When (M3):** When an action needs specific, validated values (create a task, book a slot, file an expense), or when a request is ambiguous in ways a few fields settle faster than questions. Not for open questions, and not instead of the composer — the person can always say it in words.
- **Anatomy:**
  - **Header** — What the form is for and what it is linked to: “Follow-up task · For blocker EXP-210”.
  - **Fields** — Visible label, required mark or “(optional)”, helper text, the control, and the error slot under it.
  - **Edit mark** — “Edited by you” on a field whose suggested value was changed. Aria’s message, and the review summary, say which values were suggested.
  - **Error summary** — “1 field needs a look before review.” Counts what is wrong; the detail is on the field.
  - **Progress** — “3 of 4 filled”.
  - **Review** — The values, which were suggested or edited, the confirmation sentence, and “What Aria will receive”.
  - **Outcome** — “Task created — EXP-214”, what Aria received, Undo and Open task.
- **Content rules:**
  - Say what the form is for and what it is linked to: “Follow-up task · For blocker EXP-210”.
  - Say once, in Aria’s message, that values were suggested from the source — “I suggested the owner, date and priority from the blocker”.
  - Errors say how to fix it: “Pick a date after today (Tue 6 Oct)” — not “Invalid date”.
  - The confirmation says what will happen, and where: “Aria will create this task in Orbit and link it to EXP-210. You can undo it afterwards.”
  - Failure says what happened and what is kept: “Couldn’t create the task — Orbit didn’t respond. Your details are kept.”
- **Accessibility:**
  - Every field has a visible label tied to its control; required fields are marked in the label and with aria-required.
  - Helper text and errors are linked with aria-describedby; invalid fields carry aria-invalid; errors are announced.
  - On review, focus moves to the first field that needs a look; the summary counts them.
  - Priority is a radio group with arrow-free buttons and a visible checked state; suggestion and edit marks are words, not colour.
  - The payload is a focusable, labelled region; outcome and failure are live announcements.
  - Controls are at least 44px (48px on touch); nothing animates under reduced motion.
- **Expressive:** The form rises into the conversation as Aria’s answer. Suggested values carry the agent’s mark and primary container; your edits are neutral. Errors use the error tone and an icon, never colour alone. Creating shows a calm progress label rather than motion; the result settles in with a check. Under reduced motion nothing moves.
- **Metrics:**
  - How often each suggested value is accepted, edited or cleared — a field that is usually edited should not be suggested.
  - Review → Back to edit rate, and which fields are changed there.
  - Validation errors per field; repeated ones point at unclear labels or helper text.
  - Undo after Submitted; Retry success after Couldn’t submit.
- **Precedent (names only):** Check answers — GOV.UK Design System · Error message — GOV.UK Design System · Agent-proposed actions in chat assistants
- **S2 `pkg`:** `nucleux-m3-structured-input` — not an installed package (see main §1 item 4).

### A1 · `attachments` — Attachments
- **What (M3):** A file, image or pasted block that joins the message you are about to send. It is the shallowest of the five ways to widen what an agent knows, and the only one that requires no account, no permission and no curation: you pick something, it joins the composer as an object, and the request goes out carrying it. Nobody connected anything and nothing was indexed.
- **Why (M3):** Most of what a person wants an agent to work on is sitting on their machine, and typing it out is not an option. The failure modes are all about state rather than transfer: a file that has uploaded but has not been read looks identical to one the agent can already see, so requests get fired at documents nothing has opened; a refusal that arrives after a two-minute upload was knowable before it started; and a remove control implies an undo that no product actually performs.
- **When (M3):** Whenever the material is specific to one question — this contract, this screenshot, this export. It is the right default for anything a person would not want to keep: the cost of attaching is one press and the cost of it being wrong is nothing, because it goes away with the conversation.
- **Anatomy:**
  - **Source control** — The + already in the shared composer. It offers SOURCES — upload, photo, paste — not labels. Nothing separate, because an attachment is part of the message, not a place you go.
  - **Attachment object** — One compact card per attached thing, on its own row above the input, inside the same composer. Where it sits is the claim about how long it lasts.
  - **Identity** — Name, and a type that predicts whether the agent can read it. Images get a real thumbnail because it identifies the file faster than its name; documents deliberately do not, because an invented page preview is a claim about content nobody has read.
  - **State, in words** — Uploading, Reading, Ready, Too large, Failed — written in the meta line, where a person reads anyway. Colour reinforces it and never replaces it.
  - **Progress** — A hairline along the bottom edge of the object, so it reads as that file’s progress. Determinate while there is a real number; indeterminate rather than invented when there is not.
  - **Retry** — On the failed object itself. Recovering from a dropped connection should cost one press, not a second trip to the file picker.
  - **Remove** — On every object. It is the control that raises the lifetime question, which is why it is also the control that owes the answer.
  - **Lifetime statement** — One sentence under the composer saying how long attached files last and that removal is forward-only. It is not boilerplate — it is the only place the person learns that taking a file back cannot unwrite what it already produced.
- **Content rules:**
  - Name the state in words: “Uploading”, “Reading”, “Ready”. A bar is not a label, and it is nothing at all under reduced motion.
  - Put the limit in the refusal. “Too large” sends somebody to the documentation; “Too large — 500 MB is the limit” sends them to a smaller file.
  - Say what removal does before it is pressed, not after: removing takes the file out of what comes next and cannot unwrite an answer it already shaped.
  - Describe what the agent can read, not what the file is. “Read as text only past page 100” changes what somebody asks; “PDF” does not.
  - Never write “Ready” while the file is still being read. It is a small lie that costs somebody a confidently wrong answer.
- **Accessibility:**
  - Every state is written, not only drawn. Uploading, reading, ready, refused and failed each carry a word in the meta line, because colour and a moving bar are the two cues most likely to be unavailable.
  - The attachment row is a live region: uploads finish on their own schedule, and somebody who has looked away has to be told rather than having to look.
  - Remove and retry are real buttons with labels that name the file — “Remove Northwind-proposal.pdf”, not “Remove” six times in a row.
  - Progress carries a role and, where the number is real, the value. An indeterminate bar says it is indeterminate rather than inventing a position.
  - The file picker is never the only route. Paste and drag-and-drop are alternatives, not conveniences, for anyone who cannot work a file dialog comfortably.
  - Under prefers-reduced-motion the object arrives instantly and the indeterminate bar becomes a static track. The state was in the word the whole time.
- **Expressive:** The object arriving is the one moment worth animating, and it gets a spring — a file joining a message is a user-initiated arrival and should read as one. Everything after that is restraint: the progress bar is a hairline along the bottom edge of the object it belongs to, so it reads as that file’s progress rather than the composer’s, and it is the only thing moving. Colour is state and never decoration: the primary accent marks readiness, the error container marks a refusal, and in both cases the word is already in the meta line above — the colour is reinforcement, not the message. Under prefers-reduced-motion the arrival is instant and the indeterminate bar becomes a static half-filled track, because a bar that travels to nowhere is decoration, and the word was carrying the state all along.
- **Metrics:**
  - How often a request is sent while a file is still being read — the direct measure of whether uploading and reading are distinguishable.
  - How often a file is removed within a few seconds of attaching, which measures whether the object appears early enough to catch the wrong one.
  - Retry rate after a failure, and whether the retry succeeds. A retry nobody presses means the control is not findable on the object.
  - How often the same file is attached again in a later conversation. Rising, it is the signal that this material wanted to be a knowledge base.
- **Precedent (names only):** Claude · Perplexity · Microsoft Copilot · Gemini · ChatGPT
- **S2 `pkg`:** `nucleux-m3-attachments` — not an installed package (see main §1 item 4).

### A1 · `connectors` — Connect Data Source
- **What (M3):** A card that names one external service — Google Drive, Slack, GitHub, Notion, whatever the request needs — says what the agent will be able to do with it, and opens the door. It appears in two places: a settings list, and — far more usefully — inside a conversation, at the moment the agent finds a wall. Nobody uploaded anything: what is being granted is standing access to an account, which will still be there tomorrow and can be revoked. This is a different pattern from an MCP Server Connection: a data source is one named account with a bounded, product-written scope list, never a growing list of discovered tools.
- **Why (M3):** Most of what people want an agent to do requires a system the agent has never been given, and the alternative to this pattern is an agent that says “I don’t have access to that” and stops — describing the problem and leaving the person to solve it. The risk runs the other way too. The provider’s authorisation screen is written by the party that benefits from the grant and arrives after the decision is effectively made, so the only scope list a person can act on is the one the product writes, in its own words, before the handoff.
- **When (M3):** When the answer depends on a live system the person already has an account for, and the access is worth keeping — a tracker, a calendar, a drive, a code host. It is worth offering contextually the first time a request needs it, and worth surfacing in settings afterwards so that what was granted can be re-read months later.
- **Anatomy:**
  - **The reason** — One sentence saying what the agent cannot reach and why it stopped. Only present on the contextual card, and it is what makes the card an answer rather than an advertisement.
  - **Service identity** — The service’s own mark and name, unaltered and unrecoloured, next to a name in Nucleux’s own type. Enough to recognise, not a logo wall — the person already knows what the service is, they are deciding about access to it. Everything around the mark is a Material token; the mark itself never is.
  - **Status, in words** — Not connected, Connected, Read only, Sign-in expired, Blocked by your organisation. First thing after the name, because it decides whether anything else on the card is actionable.
  - **Account** — “Connected as whom” is the real question about a connection somebody set up months ago, especially where people hold two.
  - **Scope list** — What the agent will be able to do, in the product’s own verbs, before the handoff. Marked to distinguish what is already granted from what is being asked for.
  - **The handoff sentence** — “You sign in with X. Access can be withdrawn at any time.” Not fine print — it is the difference between granting access and being asked to trust a logo.
  - **Primary action** — Named for what pressing it does next: Connect, Allow, Sign in again, Try again. Absent entirely where no press could work, which is what Blocked means.
  - **Standing-context chip** — What the connector becomes once it is live: a tonal chip in the composer carrying the service and its access level. Tonal with a chevron, deliberately unlike an attachment’s outlined card with a cross — one is a thing you took out of your machine, the other is a door you left open.
- **Content rules:**
  - Say what you cannot reach before you say what to connect. “Your issues and pull requests live in GitHub, and I have never been given it” is an explanation; “Connect GitHub” is a demand.
  - Write scopes as verbs the person can picture: “Read issues and pull requests you can already see”, not “repo:read”.
  - Name the sign-in and the exit in the same breath: “You sign in with GitHub. Access can be withdrawn at any time.”
  - Distinguish an expired sign-in from an unreachable service. They read identically as failure and they have different remedies.
  - For an admin-blocked connector, name the decision-maker and drop the button. A Connect that cannot work is worse than no Connect.
  - On disconnect, say the two things separately: what stops (new context from this source) and what does not (anything already said stays in the conversation). Silence on the second reads as deletion whether or not anything was deleted.
- **Accessibility:**
  - Connection status is a word before it is a colour or a dot. A green dot is nothing to somebody who cannot see it and ambiguous to everybody else.
  - The scope list is a real list, and the distinction between granted and requested carries a different icon as well as a different colour.
  - Every action names its outcome: “Connect Beacon”, “Sign in to Beacon again” — not “Connect” repeated down a settings page.
  - The waiting state is announced, because it resolves without anybody pressing anything and the person may have switched to the provider’s window.
  - The standing-context chip is a button with a label that says what it does, so the connection can be inspected and withdrawn from the keyboard.
  - Under prefers-reduced-motion the card arrives instantly. It was never the motion that carried the meaning.
- **Expressive:** The card arrives on a spring, because a door opening is a user-initiated event and should read as one; everything after that is restraint. Colour is state and never the whole of it — a connected service gets a dot, but the dot sits beside the word rather than instead of it, and the error tone reinforces a sentence that was already explicit. The scope list uses one shape change to carry its most important distinction: what is already granted takes a tick in the primary accent, what is only being asked for takes a chevron at reduced emphasis, so somebody re-reading an old connection can see which is which without reading either. The whole card inverts tonally when it appears inside a conversation, because there it is the agent speaking rather than a settings row, and it should belong to the turn it interrupts.
- **Metrics:**
  - How often a connector is granted at the moment it is offered contextually, against how often it is granted from the settings list. The gap is the value of offering it where the wall is.
  - How often write is granted when it was asked for alongside read — a high rate usually means nobody read the list, not that everybody agreed.
  - Time spent on the approval step. Near-zero means the scope list is decoration.
  - How often an expired sign-in is repaired versus abandoned, which measures whether that state is legible at all.
  - Requests that fail for want of a connector that was never offered. This is the number that says the wall is not being named.
- **Precedent (names only):** Claude connectors · ChatGPT apps · Microsoft 365 Copilot connectors · Gemini connected apps · Perplexity connectors
- **S2 `pkg`:** `nucleux-m3-connectors` — not an installed package (see main §1 item 4).

### A1 · `mcp` — MCP Server Connection
- **What (M3):** The lifecycle of a connection to a Model Context Protocol server, from an address nobody has validated to a tool running with somebody’s permission. One panel carries all of it: adding the server, three named steps to establish and validate the connection, the tools discovery turns up, inspection of any one of them, the approval gate at call time, the result — and the two kinds of failure, which are not the same kind.
- **Why (M3):** Anthropic is explicit that there is no technical difference between a reviewed app connector and a custom MCP server — “the runtime, transport, authentication, and tool-calling code paths are identical.” So the difference this pattern carries is not protocol, it is **epistemic**. A first-party connector has a fixed, vendor-reviewed tool surface that is known before you press anything. An MCP server has a self-declared surface that the client must go and enumerate, that can change underneath you, and whose descriptions of itself — including its own account of how dangerous each tool is — the specification says clients “MUST consider untrusted unless they come from trusted servers.” A panel that hides any of that has quietly turned a stranger’s claims into the product’s assurances.
- **When (M3):** Where an agent needs to act in a system through a standard interface rather than a bespoke integration — internal tooling, developer workflows, anything a team runs itself. It is the right pattern when the set of capabilities is genuinely not knowable in advance. It is the wrong pattern when it is: if the integration is fixed and reviewed, use a connector and spare people a capability audit they did not ask for.
- **Anatomy:**
  - **Server identity** — A mark, a name and one line of status. Before a server exists it says so rather than naming one — heading an empty state with a server name is the panel claiming a connection it has not got.
  - **Status badge** — The word, the tone and the shape of the dot: a ring while the agent cannot use this server, a filled disc once it can. Three carriers, because one of them is colour.
  - **Add server** — Name and address, on the same surface rather than a settings page, because adding a server happens in the middle of trying to get something done. Authentication is named, not configured. Transport and protocol live behind Advanced.
  - **Establishment steps** — Reaching, validating, discovering — three rows that resolve one at a time, each with its own note. They fail for different reasons and are fixed in different places, so a failure has to be able to say which. No percentage: nothing here knows one.
  - **Counts** — Tools, resources and prompts. The summary view, and enough for somebody who is not auditing anything. Zero is shown rather than hidden: “0 prompts” is information, an absent row is a question.
  - **Tool row** — What it is called, what it does, and whether it will stop and ask — availability as a word before it is a colour. The row expands; it does not navigate.
  - **Tool detail** — What it does, what it touches, whether approval is required, whether it is available. The schema and the raw annotation are one level further in, for the person who wants them.
  - **Risk band** — Reads only, Changes things, Destructive — read off the tool’s own annotations, least dangerous first, so reading down the list is reading up a ladder.
  - **Per-tool switch** — Because connecting is not consent to everything a server happens to expose, and the header says how many were declined. Disabled fades rather than vanishing, so the shape of what was declined stays visible.
  - **The gate** — At call time, naming the tool and showing the arguments. Always allow on a write, scoped to one tool on one server; withheld on anything that cannot be undone.
  - **Execution row** — Which server, which tool, what happened. All three, always — a call that runs without naming its server is a call nobody can audit afterwards.
  - **Tool failure** — Outlined, on the ordinary surface, above a tool list that is still there, with a line saying the server is still connected. The actions are about the call.
  - **Server failure** — Filled, and the badge moves. A different scope with a different fix, and the action is Reconnect.
  - **Provenance note** — One sentence saying the tool names and descriptions came from the server and are not verified here. Without it the risk bands read as the product’s verdict rather than a stranger’s claim.
- **Content rules:**
  - Say what failed, not that something failed. “Its workflow does not allow that transition” sends somebody to the right fix; “Request failed” sends them to support.
  - Keep server words and tool words apart. Unreachable, Authentication expired and Reconnect describe a connection. Failed, Retry and View details describe a call.
  - Name the risk bands in plain words. “Destructive” means something to everybody; `destructiveHint: true` means something to almost nobody.
  - Write availability as a word on the row, not as a colour on the row.
  - Say who wrote the descriptions. “Tool names and descriptions come from the server, not from this product” is the sentence that keeps the list honest.
  - Never write “always allow” next to something that cannot be undone.
  - After a disconnect, say what was kept and what was lost. A dead end is the one thing that state must not be.
- **Accessibility:**
  - The establishment steps are a live region, because they resolve on their own and the person may have looked away. Each step says Done, Working or Waiting in words, so the sequence reads without the spinner.
  - Status is never colour alone: the badge carries the word, and its dot is a ring while the server is unusable and a filled disc once it is not.
  - Availability on every tool row is a word — Available, Approval required, Disabled — before it is an icon or a tone.
  - A tool row is a button with `aria-expanded`, and its detail opens in place rather than navigating, so the reader keeps their position in the list.
  - Each per-tool switch has an accessible name carrying the tool, its risk band and its current state. The name alone is an identifier, not a description.
  - The approval gate is a labelled group and its arguments are a definition list, so what is being sent can be read item by item rather than as one run-on sentence.
  - State changes are announced: the server became ready, how many tools were discovered, a call needs approval, a call completed, a call failed, the connection expired.
  - Under prefers-reduced-motion nothing animates — not the step spinner, not the pulsing badge, not the gate’s arrival. The sequence still reads, because it was always the order of the steps that carried it and not their movement.
- **Expressive:** Restraint, because this is a security surface and a security surface that performs is a security surface nobody reads. The motion is load-bearing in exactly two places. The establishment steps resolve one at a time, and that sequence is what tells somebody which step failed when one does. And the approval gate arrives on its own easing, because a decision that fades in with everything else is a decision that gets scrolled past. Risk is carried by grouping and by words before colour: the bands read “Reads only”, “Changes things”, “Destructive”, availability is a word on every row, and the status dot is a **ring** when the server cannot be used and a filled disc when it can, so the difference survives greyscale. The error container is spent once, on the call that cannot be undone; a routine write asks on a tonal ground, because a panel that shouts at every create teaches people to approve without reading.
- **Metrics:**
  - How often a tool is inspected before the server is used. Near-zero means the list is decoration and nobody is deciding anything.
  - How many tools are switched off, and which. A server whose writing tools are switched off by nearly everybody is a server asking for too much.
  - Approval versus denial rate on gated calls, and how long the decision takes. Instant approval every time means the gate has become a speed bump.
  - Tool failures and server failures, counted separately. Pooling them hides both, and they have nothing to do with each other.
  - How often a retry escalates to a reconnect. A high rate means the connection is expiring silently and the tool error is the first anybody hears of it.
  - Failures at each establishment step, separately. Reach failures and authentication failures send people to different places.
- **Precedent (names only):** MCP specification · Claude Code · ChatGPT connectors and developer mode · Cursor and VS Code · Tool annotations as risk vocabulary

### A1 · `knowledge-base` — Knowledge Base
- **What (M3):** A named set of sources an agent can read whenever it is working in a given scope: a project, a workspace, a custom assistant. The surface says four things and nothing else. What is in the base. Whether each source is usable yet. Whether the base is being read right now. And, after an answer, which sources it actually read.
- **Why (M3):** Re-attaching the same material to every conversation is both tedious and unreliable — people forget, and the answer quietly gets worse without saying so. Making the material standing fixes that and introduces three confusions that an attachment never has, because a file dropped into a message is usable the instant it lands. Here, **added is not ready**: a file that has arrived has not necessarily been read. **Ready is not in use**: a base can be perfectly prepared and have contributed nothing to the answer on screen. And **one source is not the base**: a password-protected PDF is a problem with that PDF. A panel that blurs any of the three will be trusted at exactly the moments it should not be.
- **When (M3):** Where the same material informs many conversations — a research corpus, a policy set, a product’s own documentation, a team’s accumulated notes. The test is lifetime. If somebody would be annoyed to re-upload it tomorrow, it wants to be a knowledge base. If they would be alarmed to find it still there tomorrow, it wants to be an attachment, and the moment a file crosses that line somebody should have agreed to it.
- **Anatomy:**
  - **KnowledgeBaseSummary** — Mark, name, counts and status. The resting representation, and compact on purpose — most of the time the question is which scope am I working against, not what is in it.
  - **KnowledgeBaseStatus** — One badge reading No sources yet, Preparing, Available, Active, In use, Partly available, Needs attention or Not active. Derived from the sources and the project rather than stored beside them, so it cannot disagree with the list under it.
  - **KnowledgeScopeChip** — Where it applies, and in which of the two senses. “Available in this project” says it could be used here; “Active in this project” says it will be. The composer chip is the same fact while somebody is typing.
  - **KnowledgeSourceList** — Progressive disclosure. Closed by default, open while sources are preparing or a row needs a person, with optional status grouping and a cap that promotes trouble above the fold rather than truncating it below.
  - **KnowledgeSourceItem** — One source: kind, freshness written for that kind, readiness as a word, and the one action that fits its state. An uploaded source carries a capture date; a linked one says it follows the original.
  - **KnowledgeSourceStatus** — Preparing, Ready, Needs refresh, Couldn’t be read, Unavailable. The last two are separate because they are fixed in different places — Retry and Replace against a file that would not parse, Reconnect against one you may no longer open.
  - **KnowledgeActivity** — Searching this base, then reading a named number of sources. Live, and gone when it finishes. No percentage, because nothing in the client knows an honest one for reading a document.
  - **KnowledgeProvenance** — “Used 4 sources from Product Research”, each one inspectable. This is what makes a standing scope checkable rather than merely trusted.
  - **KnowledgeEmptyState** — What a source buys that an attachment does not — it outlives the conversation — and one action. Not a marketing screen: there is nothing to sell, only a distinction to explain.
  - **KnowledgeNoResult** — It looked and found nothing, with the actions the product can actually perform. Distinct from every failure state, because the base worked.
  - **KnowledgeBaseList** — Several collections, one project, each row carrying its own count and the word Active or Available. A list, not a dashboard.
  - **KnowledgeRemoveDialog** — Names the source, says what the agent will stop doing, and says what is not happening. Removing a source and deleting a base are two destructions and must never share a control.
- **Content rules:**
  - Name the scope, and use the right verb. “Available in this project” and “Active in this project” are two different promises, and a product that prints one line for both leaves nobody able to tell whether their question will be grounded.
  - Write readiness as a word on the row — Ready, Preparing, Needs refresh, Couldn’t be read, Unavailable. A tint and an icon may repeat it; neither carries it alone.
  - Describe an uploaded source and a linked source differently. “Uploaded 2 days ago” is a capture date; “Linked · follows the original” is a relationship. One sentence for both is a promise the product cannot keep.
  - Count both halves once either half is in trouble: “11 available · 1 unavailable”, never “12 sources” beside an amber badge.
  - Say what an answer used, in the user’s terms: “Used 4 sources from Product Research”, with the four named.
  - When nothing matches, say so plainly and name the base you searched. “I searched Product Research and couldn’t find anything about pricing in it” is a good answer; a confident paragraph is not.
  - In the remove dialog, spend the sentence on what is *not* happening. That is the only thing the dialog is for.
  - Never show RAG vocabulary. Embeddings, vector stores, chunk size, index status and retrieval scores are all real, and none of them are the user’s problem.
- **Accessibility:**
  - Base status is announced as a word in a labelled region, not conveyed by badge colour. Preparing, Available, Active, In use, Partly available and Not active all read identically in greyscale.
  - The badge dot is a ring while the base cannot be used and a filled disc once it can, so the one distinction that changes behaviour survives with no colour perception at all.
  - Every source row states its readiness in text before any icon, and the spinner on a preparing row is aria-hidden — the word was carrying that state the whole time.
  - Row actions carry the source name in their accessible label, so a column of Remove buttons is not a column of identical labels.
  - The remove dialog is a real alertdialog with aria-modal, labelled by the question it is asking, and Cancel is reachable first.
  - Meaningful changes are announced as they happen: the base is active, searching, reading four sources, one source is unavailable, no relevant information found, a source was removed and the base is unchanged.
  - Under prefers-reduced-motion the in-use pulse and the row spinners stop and hold at partial opacity. Nothing that was only carried by motion is lost, because nothing was only carried by motion.
- **Expressive:** This is furniture somebody returns to, not a moment they are taken through, so it is quiet by default: a card, a status word, a list that is closed until there is a reason to open it. Motion is spent in two places that earn it. The badge dot is a **ring** while the base cannot be used and a filled disc once it can, so the most important distinction on the surface is a shape rather than a colour. And the in-use band pulses while the agent is reading, because that is the one genuinely live thing here — deliberately not a progress bar, since nothing in the client knows an honest percentage for reading a document. The failing row is outlined in error rather than flooded with it: the base is still usable, and a filled error row would say otherwise.
- **Metrics:**
  - The share of answers that show provenance, and how often it is opened. It measures whether grounding is being used or merely displayed.
  - How often No relevant knowledge is reached, and what people do next. Rising is not failure — it usually means the scope is narrower than people expect, which is a content problem, not a UI one.
  - Time from a source being added to it being usable, and how often somebody asks a question inside that window. That gap is where added-is-not-ready does its damage.
  - How long a base sits partly available. A row-level failure nobody fixes for a fortnight is a base quietly answering with less than it claims.
  - How often a base is switched off versus deleted. If the two are close, the wording is not doing its job.
  - How often the same file is attached to a conversation whose base already covers it — the signal that the active scope is not visible enough.
- **Precedent (names only):** Claude Projects · ChatGPT Projects · Gemini Gems knowledge · Cursor project context · NotebookLM

### A1 · `model-selection` — Model Selection
- **What (M3):** A small control in the shared composer carrying two values — which model, and how hard to think — and a menu behind it where every option says what it is **for** rather than what it is. There is no second control and no settings page: a choice that only matters at the moment of asking belongs where the asking happens.
- **Why (M3):** Every question somebody actually has about a model is comparative, and a list of names answers none of them: what is this one for, what does it cost me, what happens to this conversation if I switch, and do I have to decide at all. The failures are specific and they are all shipping today. Products bundle a spec sheet into a dropdown nobody reads. They ship a router that claims to pick for your task while it is really balancing capacity. They let a rate-limited request fall back to a model that does not appear in the picker at all, and tell nobody. And almost none of them says whether switching mid-conversation rewrites what was already said — a question with an obvious answer that is nevertheless never given.
- **When (M3):** Where models differ in ways a person can act on — speed, depth, what the request costs them — and where the person, not the product, owns the prompt. It belongs in professional and enterprise tools where explicit control is a requirement, and it belongs wherever somebody is choosing to wait longer for a better answer.
- **Anatomy:**
  - **ModelChip** — The resting control, inside the composer that every other pattern already uses: ONE kit Small text button reading “Balanced High” — the model in the label weight, the effort value quieter beside it, so it reads as a name and a value rather than one setting with a dot in it. It is the composer’s own mode slot rather than a control added beside it, and there is no ModelComposer.
  - **ModelPicker** — A list, not a catalogue. Auto at the top, a separator, then the models. One highlight travels between rows for pointer and keyboard alike, rather than a tint blinking on and off under the cursor.
  - **ModelOption** — Name, one line saying what it is FOR, and at most one attribute. Never a specification table — context windows and parameter counts belong where somebody is comparing on purpose rather than choosing mid-thought.
  - **AutoSwitch** — A toggle at the top of the list, above a separator, with one line underneath, shown on or off, saying what it weighs — quality and speed. A switch rather than a sixth radio because Auto is not one more thing to pick — it is the question of whether you pick at all, and turning it on collapses the list it replaces rather than leaving rows you can see and cannot use.
  - **EffortScreen** — The second screen of the same flyout. Choosing a model row (or turning Auto on) replaces the list with it: a breadcrumb — back chevron, the model, its effort value — and the slider, nothing else. The breadcrumb is the way back to the list. The two axes stay two settings; only the trigger is shared.
  - **EffortSlider** — Five notches and one handle. Effort is ordinal, and a column of radios says nothing about that ordering; a track says it in the shape of the control. One tab stop carries the value; arrows, Home and End move it, and the notches are pressable but silent. The active track stops short of the handle, which is M3 Expressive’s own anatomy and what keeps the handle from vanishing into the fill.
  - **AvailabilityTag** — Temporarily unavailable or Restricted, in words. One field with three values rather than two booleans, because “restricted and unavailable” is a sentence no product can write.
  - **ChangeNote** — When a change starts mattering — next message, this conversation, or everywhere. Said once, after the change, where it is a fact rather than a standing warning at the bottom of a menu nobody reads twice.
  - **FallbackSurface** — The recovery when the selected model can no longer be used. Both ways out, and the sentence people actually need: the conversation is unchanged.
  - **ModelCredit** — Which model actually produced an answer. Optional, and most needed under Auto — where the whole point is that the answer did not come from a fixed model.
- **Content rules:**
  - Write each option as a task, not a specification: “More depth for complex, multi-step work”, not “200K context, 64K output”.
  - Say what it costs in the person’s own currency — their allowance, their waiting time — not in tokens.
  - Answer the switch question once, after the switch: “Using Deep reasoning from your next message”. A standing sentence at the foot of the picker is read once and then never again, and it competes with the options for the whole time it is there.
  - Keep the effort screen to where you are and the one control that changes it: a breadcrumb naming the model and its effort value, and the slider. The step’s own meaning belongs in the slider’s accessible value, not in a permanent line of prose.
  - Name the router’s objective. “Automatic” alone asks for trust; “picks the cheapest model that can do it” earns it.
  - On a blocked row, say what to use instead. “Temporarily unavailable” on its own is half a sentence.
  - Word the two blocks apart. Temporarily unavailable ends in waiting; restricted ends in a person, and offering a retry there sends somebody round a loop that cannot close.
- **Accessibility:**
  - The chip is a button with an accessible name carrying both values and what pressing it does — not just the model’s name, which is an identifier rather than a description.
  - The menu is a real menu and the options are radio items reporting their checked state, so “which one is selected” survives having no colour perception at all.
  - Selection is a tick as well as a tonal background. One of those is invisible to some people and the other is not.
  - Where a model is unavailable because of an allowance, the row is disabled and still readable, because the sentence about what answers instead is the useful part.
  - Where a model is unavailable because of an organisation’s policy, it is absent rather than disabled, and one line explains the shorter list — a control nobody may operate should not be reachable at all.
  - Opening and closing the menu is announced, and the label change after a selection is the confirmation — no separate toast is needed and none should be added.
- **Expressive:** The smallest expressive budget of the five, deliberately: this is a control somebody touches for two seconds on their way to asking something. The resting chip does not move at all. The menu is the only moment with any motion in it, and what it spends that on is hierarchy rather than spectacle — the selected row takes a tonal wash and a tick, the recommendation and the router take tags rather than colour, and the option being chosen is never animated on selection because the thing that should change is the label, immediately. Selection state is carried by a tick as well as a background, so it survives being read without colour. The one place an accent is used at strength is a substituted answer, where the error container marks that you did not get what you asked for.
- **Metrics:**
  - How often the selector is opened and closed without a change, which measures whether the menu is answering the question or just being read.
  - The share of requests on the router. A product where nobody leaves Auto on has made it untrustworthy.
  - How often a switch is followed immediately by a re-ask of the same question — the signal that people expect switching to be retroactive.
  - Substitution rate, and whether attribution is noticed. If nobody reacts to being substituted, the notice is not visible enough.
  - For administered deployments: how often people ask for a model they cannot see. Rising means the absence needs its explanation strengthened.
- **Precedent (names only):** Claude · Claude for organisations · GitHub Copilot · Cursor · Microsoft Copilot · Why not to expose it
- **S2 `pkg`:** `nucleux-m3-model-selection` — not an installed package (see main §1 item 4).
