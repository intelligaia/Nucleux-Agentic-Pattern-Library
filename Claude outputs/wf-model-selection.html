Model Selection

Reusable agentic pattern · Nucleux · wireframe and state model

Low fidelity — structure and behaviour only, no visual design

The question the pattern answers

“What capability will handle my request?” — answered without anyone needing to know a model ID, a parameter count or a routing rule.

Three things sit near each other here and are not the same setting. Model is which capability answers. Effort is how hard it thinks. Mode is how the product behaves. This pattern owns the first two and keeps them on separate axes; it does not own the third.

3 · The nine states

1 · RESTING

A selection is already made

Nobody is asked to choose before their first request. A strong default is already in the chip.

Balanced · Standard ▾
2 · PICKER OPEN

The list above, anchored to the chip

Arrow keys move, Enter selects, Escape closes and returns focus to the chip. The prompt text is untouched throughout.

3 · SPECIFIC MODEL SELECTED

A deliberate choice

The user picked one capability. No router icon: what runs is what the chip says.

Deep · Thorough ▾
4 · AUTO SELECTED

The product chooses per request

Auto carries a router mark and states what it optimises for. It must never read as a fixed model — and the objective is the one thing that makes it trustworthy.

5 · MODEL CHANGED

Acknowledged, not celebrated

The chip updates and one line says when it takes effect, in the scope the host actually supports. No success screen, no toast, no confirmation dialog.

5 · Data model

Nothing product-specific is baked in. No provider name, no model name, no tier vocabulary — the host supplies all of it, and the component renders whatever it is given.

model = {
  id, label,
  for,            // one line: the KIND OF TASK, not the capability
  note,           // one line of consequence; on a blocked row, what to use instead
  provider,       // optional — grouping is only drawn when the host asks for it
  costTier,       // optional — 'low' | 'standard' | 'premium', never raw pricing
  capabilities,   // optional — ['tools', 'images']; shown only where they differ
  recommended,    // at most one
  router,         // Auto. NOT a model, and never rendered as one
  availability    // 'ok' | 'unavailable' | 'restricted'
}

selection = {
  kind,           // 'auto' | 'model'
  modelId,
  effortId,       // the second axis, independent of modelId
  aimId,          // what Auto optimises for — meaningless unless kind is 'auto'
  scope           // 'request' | 'conversation' | 'workspace' — host-defined
}
Availability is one field with three values, not two booleans. Two booleans permit “restricted and unavailable”, which is a sentence no product can write.

6 · What this pattern refuses to do

Not thisBecause
Auto as another model rowIt is a decision procedure. Drawing it as a peer makes people think one fixed model is running.
Effort folded into the model listTwo axes. “Deep · Quick” and “Swift · Thorough” are both legitimate and neither is expressible if they are one list.
Slower described as betterDeep is not better than Swift for a one-line draft. Rows say what a thing is for.
Specifications on every rowContext windows and parameter counts belong in developer documentation, where somebody is comparing on purpose.
Restricted drawn like unavailableOne is waiting; the other is asking a person. Same treatment sends people to the wrong recovery.
A model change resetting the threadChanging who answers next is not the same as starting again.
